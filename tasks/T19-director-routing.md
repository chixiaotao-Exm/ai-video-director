## 已确认的问题

- 任务 `7ec61a17-acd2-4682-bc1b-ba8823979c83` 累计尝试 11 次；持久化的失败信息是 HTTP 429、`QUOTA_EXHAUSTED`、`Individual quota reached`，服务错误中命名了 `claude-opus-4-6-thinking`。这是当时的额度错误，不能据此断言当前仍无额度。
- 原设置是 `director_provider=openai`、`director_model=claude-opus-4-6-thinking`。选择接口没有同时选择模型，模型输入又藏在另一服务卡片中，容易误以为已切换成 GPT。
- 旧任务的 `model_key` 只用于队列分组，不足以证明实际请求模型。当前设置也不能证明历史任务调用了哪个模型。
- 导演通知每次重试都写入一次相同系统消息，造成重复对话；SDK 隐式重试又叠加队列重试。
- 原“测试连接”固定拿脚本或导演字段，可能与被测试服务的有效角色路由不同。
- 明确切换到 `openai/gpt-6-astra` 后，原任务仍多次收到上游 HTTP 524，约 16.5 秒失败。短连接测试成功不能证明完整导演报告可用；也不能把这个观测直接解释成固定的 Cloudflare 超时时长。
- 同一份完整导演上下文（26 条消息、29 个工具、30,768 字节）使用 Responses 流式请求后成功：1.828 秒收到首事件，57.734 秒完成，6007 输入 / 1711 输出 token。该诊断没有执行工具。证据为 `data/t19-director-20261021/full-payload-stream-probe.json`。
- 同步聊天异常原来返回非 JSON 的 500，前端直接解析 JSON，掩盖了真实的上游错误，显示“服务器返回无效响应”。

## 修复行为

- 导演表单集中编辑服务与明确模型 ID，显示有效路由；切换服务后须明确选模型。保存同时更新 `llm_routes.director`，保留其他角色。高级 JSON 草稿不能覆盖更新的导演路由。
- 新导演、子 Agent、分析、脚本任务捕获提交路由，自动重试保持该路由。手动重试导演任务采用当前保存的导演路由，并保留之前请求的证据。
- 路由层在预算校验通过、请求派发前记录服务/模型/角色/尝试次数；分析另记本地 Whisper 步骤，后台搜索调用也归入所属任务。
- 项目最近任务、全局任务和唱跳任务共用展示：`actual` 为程序发出的请求路由，`snapshot` 为任务配置，`queue_marker` 为未经实际调用验证的旧队列标记。网关内部是否转发到另一模型仍以网关记录为准。
- 额度耗尽、鉴权失败和无效请求停止自动重试；短时限流、超时和服务临时错误保留队列重试。OpenAI/Anthropic SDK 的隐式重试关闭，避免层层重试。
- 失败摘要和恢复时间可读，详细错误继续折叠保留。旧错误中的相对恢复时长不会从读取时间重新计算。
- 导演后台事件使用任务 ID 去重。失败后复用已有通知和工具结果；结果未持久化的工具调用不会盲目重复执行。历史重复消息不做破坏性清理。
- 连接测试可指定角色，返回实际测试的角色与模型；不能把其他服务的角色字段当成本服务的模型。
- GPT-6 Astra 的 OpenAI 路由使用流式 Responses，完整接收后再解析工具调用。保存原生推理、阶段和工具调用块，后续请求复用时避免重复工具调用；不在失败后自动切换端点重发。
- 流中额度、鉴权、请求、限流、超时和连接失败保留安全分类及可获得的用量；分类在隔离 worker 的 traceback 序列化后仍有效。收到完整 `response.completed` 即返回，不因后续传输断开重新执行已完成推理。
- 同步聊天返回安全的结构化错误；前端也能处理文本、HTML 或损坏的错误响应，保留 HTTP 状态并给出可读摘要，不展示原始上游页面和敏感信息。
